# 火力全开改造（2026-11-15）

目标：固定用户选定模型，把增加的开销用于可检查的完成度、修复与候选择优。

## 已实现

- 探测 Windows 可用物理内存、逻辑 CPU、项目盘与候选工作区所在盘的剩余空间。内存或磁盘未知时使用单路。
- 候选安全上限从 3 提至 6；按 CPU、可用内存、磁盘、上下文、用户上限和项目收紧配置共同限制。allout 候选使用独立的 allout 上限，不再被子代理默认 3 路间接卡住。
- 资源估计预留 2 GiB，按每候选 2 GiB 内存/磁盘估计。此为保守启发式，不是峰值保证；尚未测量每个仓库的实际工作树成本。
- 已有判据：先单路，失败后修复，再以不同策略分叉；首个候选通过后最多等待 30 秒，供已有路线交卷择优。超时及用户中断均回收候选。
- 无判据时，模型实现后可提出测试命令和验收文件清单。用户批准后复核文件指纹，执行测试并按失败结果进入修复与择优。没有有效提案或用户拒绝时，执行同模型证据审阅，标注缺少独立验收。
- 主会话锁定期间侧路调用继承推理强度；候选也锁模型。识别 xhigh。
- 判据反馈按上下文放大为 6000 / 12000 / 24000 字符，截断明确标注。
- 桌面入口可设置候选上限和本轮并行验收许可。执行卡片展示资源读数、候选状态与择优结果。显示与执行使用同一计划快照。
- 并行验收和候选内部只读探索共享本轮资源名额。并行验收须明确勾选，最高三路。候选内部继承锁定模型和只读工具权限。
- 根据机器调整每段步数，保持配置给出的总步数额度。分叉提示包含前序失败输出、修复涉及文件、修复结果和改动是否保留。

## 对原建议的调整与边界

- 用户总步数、费用和权限仍为上限。资源名额按回合计算。
- 共享数据库、端口或服务的测试使用默认串行。并行选项由用户按回合确认，执行器按原命令运行。
- 两个小任务的对照只验证同模型端到端交付，复杂任务和多个候选的实测质量收益仍待扩大样本衡量。

## 自建判据与候选择优复测

- 用同一 OpenCode 默认模型从零实现首个不重复字符的查找。模型新建 pytest 文件并提出命令，测试驱动只批准约定的临时项目命令和文件。正式验收通过 12 项，回合返回达成，记录费用约 ¥0.01063。
- 在独立临时 Git 仓库直接驱动双候选编排，仓库和配置均为测试专用。合并闭区间任务的两份候选都通过，但修改前的真实模型评审超过 130 秒实验限时，未写回。
- 评审现在分别接收两位候选的判据输出。单次评审最多 45 秒，整组评审最多 90 秒。缺少对调结论的一对比较按无票处理，照常根据可复核的候选数据择优。空补丁不会进入排序。
- 更新后用区间裁剪任务再试。两路真实候选都通过，评审达到 90 秒上限，未取得可计分的对调结论。排序按可复核数据选中候选，写回前主工作区干净，写回后公开测试和独立隐藏测试通过。端到端 125.5 秒，记录费用约 ¥0.01030。本次直接调用双候选编排检验写回，生产环境仍按实际硬件推导。受限时的回退已实测，真实模型评审按时给出成对结论仍未验证。
- 相关 allout 回归 142 项通过，更新后的排序专项 5 项通过。排序测试核对两份证据随 A/B 位置对调，缺失的对调结论不会引入单侧票。

## 真实模型评审稳定性复测

对 OpenCode 的短评审请求分段计时。最高推理档约 5.6 秒，默认档约 3.9 秒，都能正常返回可解析结论。另在一次完整回合中捕获到 OpenCode TLS 建连超时并自动重试。现有证据说明网关能处理这种评审请求，慢请求不全是解析问题。

使用真实 Git 补丁和同一个 OpenCode 模型复测生产排序。三组候选分别比较倒序边界检查、Unicode 大小写、是否修改输入。每组两个候选的公开判据都相同，预先按额外需求确定正确候选。两次位置对调均选中了正确候选，三组分别耗时 13.39、14.64 和 10.26 秒。费用合计约 ¥0.00832。

位置对调的两则独立评审现在并行执行，一对最多等 45 秒，多对合计最多等 90 秒。卡片显示完整评审对数，并提示没有可计分对照时已按验收结果择优。

更新后完整火力全开回合使用临时仓库和两路资源夹具。主路线未通过公开测试，两个真实候选都通过。并行评审达到 45 秒上限，自动选择已经验收的补丁，写回、交付复验和隐藏测试均通过。公开测试未改动，回合返回 `met`，交付标记为 `verified`。整轮 154.5 秒，已记录费用约 ¥0.02409。

连接对照里，共用与独立连接都收到了推理内容，随后均超过 45 秒。没有确认连接复用是慢评审的原因。另发现客户端把流结束字段存在共享对象上，并行响应可能互相覆盖。该状态已改为每条流独立记录。选票解析只接受最后一行的正式结论。

再用并行评审复测两组已知优劣的 Git 补丁。两组都在限时内完成两次位置对调，正确候选各获两票，分别用时 7.4 秒和 6.1 秒。已记录费用合计约 ¥0.00501。

本轮回归覆盖后端全量 2717 通过、17 跳过，流与排序补测 47 通过，正式结论解析和排序补测 19 通过，前端 415 通过，Electron 37 通过、2 跳过。真实模型仍会遇到网络和推理耗时波动，正常评审和超时回退均已验证。

是否提高解决率。**

**已知噪声**：本轮 `public_changed` 曾把 pytest 生成的 `__pycache__` 算进"公开测试被改动"
（已改为只看源码），该字段不作为本轮结论依据。

**下一步**：在 ≥2 路资源的机器上重复（每任务至少 3 次），补更难的、plain 会失败的任务；
结果写回本节，并保留每样本的 JSON（`research/bench/allout/out-all.json`）。


## 2026-11-15 多路复测（清理后台后：可用内存 8.72 GB）

同一台机器，可用内存从 4.1 GB 升到 8.72 GB 后重新推导：
`candidates=3, limiting=resource, per_lane=2.0, judge_slots=1, explore_slots=1`
——**多路是资源推导出来的，不是配置写死的**。

### 多路是否真的启动

`03_wrong_approach` / `04_green_but_missing` 用 `--candidates 2` 复跑，首轮判据直接通过，
`fanout_started=0`（没有分叉；这是"预算不是配额"的正常结果）。

为了验证分叉路径本身，新增 `99_fanout_smoke`（判据恒 `exit 1`，只做机器冒烟）：
`fanout_started=2`，两个候选都经历了
`preparing → working → queued → testing`，其中一路 `cancelled`；600s 墙钟上限到达后本轮被
中断并回收候选，**没有误报 `met`**（判据恒失败、隐藏验收通过也不报 met，符合交付闸门）。
该样本 `delivery` 为空（中断在闸门之前），记录为超时。

**本轮没有观察到的**：两个候选都通过判据 → A/B 评定 → 写回 → 交付复验的完整多路闭环。
冒烟夹具的判据恒失败，候选不可能通过；而四个质量任务都被单路首判解决了。
这部分目前由单元测试覆盖（`test_allout_rank.py` 的成对评定/缺票回退、`test_allout_run.py`
的写回失败与回归门），但仍缺一次真实模型下的"双候选都通过→择优→写回"实测。
