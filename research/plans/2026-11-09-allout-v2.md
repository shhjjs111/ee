## 0. 一句话与定位

一个会话级开关。打开后，ee 把**这个模型、这台机器、这个项目**能给的全部推理预算，花在「让活真正通过验证」上。

用户定义（2026-11-09 当面给出，本文最高优先级）：

> 基于用户电脑配置和模型，真正的火力全开，让模型最大程度接近极限能力，做出模型极限的东西。

两条推论，全文所有取舍都从这里来：

1. **模型不换。** 用户选了哪个模型就只用哪个模型。候选生成、排序、修复、判定全部是同一个模型。不调用 `Session.set_model`、不用 `task` 工具的 `model` 参数、不借用 `roles.explore` / `roles.compact` / `roles.title` 等按用途分模型的既有配置。理由：用户可能只有一个模型；换模型还会整段作废前缀缓存（`session.py` 的 `set_model` 注释）。
2. **不是「多跑几遍」。** 预算不是配额：一次就过就零额外成本；失败先修，修不好才分叉。N 是上界，不是次数。

唯一可调的是**同一模型的推理强度**（一个请求参数），而且只在新会话开场设定——已有会话中途改档会整段断前缀缓存（`ee/core/session.py:393` 的注释写明）。

## 1. 调研结论：什么真正决定「逼近极限」

2026-11-09 用真实浏览器核实了 v1 引用的全部 9 个来源（来源清单与核实方式见 §13）。按证据强度排序，决定上限的是下面五件事，而不是「并行路数」。

### 1.1 执行判据门控（第一优先）

LLM-as-a-Verifier 与 agent-ultramode 的一致结论：**只读轨迹的验证者会被「自信但错误的自述」骗过**。ultramode 论文里 extract-elf 一例：失败候选报告「4102 条、零不匹配」，正确答案其实是 698，验证者信了。这类错误只有**真跑测试**能纠正。

所以：只有项目真实的测试命令通过才算成功（复用 `goal.Verdict`，v1 已定）；候选之间先比「是否通过判据」，再谈任何其他信号。模型自述永远不参与判定（沿用 `bestof.py` 的既有不变量）。

### 1.2 批评引导的修复 + keep-policy（唯一能越过 oracle@N 的机制）

- 纯代码任务（SWE-bench Lite 24 题，真实测试判定）：base@1 70.8% → 选优 75.0% → 修复 87.5% → keep-policy **91.7%**，高于候选池 oracle@5 的 87.5%。
- keep-policy：修复只有在「判据不变差且严格更好」时才保留，否则丢弃、回到胜者。保证修复不会让结果变差。
- **诚实边界**：同一机制在 Terminal-Bench 上是空结果（40% < 60% oracle）。本功能面向「有可执行判据」的代码项目，不承诺终端类任务。

### 1.3 同模型 reasoned A/B 排序（选择是第二瓶颈）

- 对通过判据的候选：让**同一个模型**读两个候选（任务说明 + 各自 diff + 判据输出），写几句分析，最后一行给 `FINAL: A` 或 `FINAL: B`；**位置对调各评一次**，抵消位置偏差。
- 证据：ultramode 在论文自己的 89 题轨迹上 87.6%，平 logprob SOTA 的 88.0%±0.6，验证调用少 7.5 倍（576 vs 4320），且**不需要 logprobs** —— ee 接的所有模型都能用。
- 这替代 v1 §8 的「同分按成本排序」：成本只在判据、回归门、票数、测试数全部相同时做最后一级。

### 1.4 预算自适应（省掉一半浪费）

- AI21：约 50% 任务单次 rollout 就解决；级联早停最多省 44% 算力；并行早停最多快 25%。
- 最优停止（arXiv 2510.01394）：同等质量少 15–35% 次生成。
- compute-optimal 分配（arXiv 2408.03314）：比 best-of-N 效率高 4 倍。
- 落地：默认 1 路 → 失败修 1 轮 → 还失败才分叉 2~3 路；任何一路通过判据立即取消其余。

### 1.5 同一次采样内的多样性（N 的上限很低）

- Stroebl 等（arXiv 2411.17501）：假阳性率给重采样设死上限，最优采样次数常小于 10，成本比高时 K≤5。所以 **N 硬上界 3**，预算优先给修复而不是重采样。
- ultramode 用温度阶梯（0 / 0.3 / 0.6 / 0.9 / 1.1）制造候选差异。ee 同款：每个候选克隆一份 config，覆盖该模型条目的 `temperature`（`config.resolve_model` 把模型表字段当档案覆盖项，零核心改动）。

## 3. 火力如何推导（`AlloutPlan`）

判据来源优先级：用户显式填写 > 项目文件探测（首次需确认）> 无（降级）。

```python
@dataclass(frozen=True)
class AlloutPlan:
    candidates: int          # 分叉路数（1 = 不分叉）
    repair_rounds: int       # 批评修复轮数（0/1/2）
    max_rounds: int          # 判据判定的总轮数（沿用 goal 的 max_rounds）
    effort: str              # 新会话应使用的推理强度档（"" = 不支持的模型，按默认）
    max_steps: int           # 单个候选的步数预算
    temperature_ladder: list # 每个候选的 temperature
    reasons: list[str]       # 界面直接显示
    degradations: list[str]  # 降级原因（空 = 无降级）
    verified: bool           # 是否有客观判据；False 时只单路 + 标注「未验证」
```

推导规则（逐条产出 `reasons`）：

- **effort**：`profile.effort_param` 为空 → `""`（不发参数，reasons 写明「该模型不支持调节」）；否则取 `effort_levels` 的最高档。只在新会话生效。
- **candidates**：`min(cpu//4 钳到 1..6, 3 硬上界, context_window>=128k ? 3 : 1, subagent.max_parallel)`。依据：本项目实测 `-n auto`（16 路）会红 2 条、`-n 8` 全绿——判据命令本身吃 CPU，超载产出假失败。
- **repair_rounds**：有判据 → 1；候选分叉后若全部失败 → 再加 1（总上限 2）。
- **max_steps**：`config.max_steps` 不放大（步数预算已是分段续跑口径）；候选会话沿用。
- **temperature_ladder**：`[0.0, 0.3, 0.6, 0.9, 1.1][:candidates]`；模型档案显式设了 `temperature` 时以档案为首项、阶梯从次项起。
- **verified**：判据为 None → `False`，`degradations` 写明「只能单路尝试，结果标注未验证」。

预演（16 核、128k+ 上下文）：

| 模型档案 | effort | candidates | 说明 |
|---|---|---|---|
| deepseek 1M | max | 3 | |
| gemini 1M | 最高档 | 3 | |
| gpt 272k | max | 3 | |
| claude 200k | ""（不支持） | 3 | reasons 写明按默认档 |
| kimi / glm / qwen / doubao 131k+ | 部分支持 | 3 | 131072 刚好过 128k 门槛 |
| 8 核机器 | 任意 | 2 | `by_cpu` 限制 |
| 4 核机器 | 任意 | 1 | 只单路 + 修复 |

## 4. 执行流程（修订）

```
开关打开
   ↓
【探测】probe.py 只读项目文件 → 判据命令 + 测试文件清单
   ↓ 无判据 → 降级：单路 + 标注「未验证」（零分叉、零修复加注）
   ↓ 有判据（首次需用户确认一次，写入会话 meta）
【轮 1】单路（温度 0）正常做 → 判据（串行）
   ↓ 通过（约 50%）→ 结束，零额外成本
   ↓ 失败
【轮 2】批评修复：同模型写「差在哪」→ 据此修 → 判据 + 回归门
   ↓ 更好且不回归 → 保留并结束
   ↓ 仍失败
【轮 3】分叉 2~3 路（温度阶梯、各自 worktree、判据串行）
         每路自己跑「做 → 判据」，通过的立即报回，取消其余
   ↓
【排序】通过的候选 > 同模型 A/B 两两评（位置对调），净胜者
   ↓
【写回】git diff --binary agent_base..HEAD → git apply 到主目录（脏目录可用）
        → 刷新主会话当回合 tree_after
   ↓
【清理】落选候选 finish_agent 保留（不删）；取消的也一样
   ↓
【报告】goal_check / goal_done → 界面；写明每路用了哪条规则
```

关键约束：

- **判据串行**：所有 `judge()` 调用排队执行（一个 `asyncio.Lock`），并发会互相抢 CPU 造出假失败。
- **回归门**：候选写完后，除目标判据外，还要跑「改动前已通过的测试」清单（探测阶段记录，或用户填的 PASS_TO_PASS 命令）；回归即失败。
- **候选会话**：`Session(..., persist=False)`，模型 = 主会话当前模型，`effort` 与主会话一致；禁用 `task` 工具（不嵌套）。
- **预算**：候选共用主会话的 `BudgetGuard`；分叉前先查 `stop_reason`，已到线不分叉。

## 5. 判据探测（`core/probe.py`）

只读项目文件，**不跑命令**。覆盖 v1 §5.1 的九种，另加两处修订：

- 返回 `{"command", "source", "confirmed": False, "test_files": [...]}`。`confirmed` 由 `Thread.meta["allout"]["goal_confirmed"]` 决定：探测来的判据首次使用需在界面确认一次（陌生仓库不能让 ee 自动执行它的测试脚本），用户自己填的判据不需要。
- `test_files` 来自 git 文件清单里匹配 `**/test*_*`、`*_test.*`、`*.test.*`、`*.spec.*`、`tests/` 的路径集合，供 A/B 提示「谁动过测试」与回归门使用。
- **gradle 例外**：成功时默认没有汇总行，判据会读到 0（zero_tests）→ 界面提示「需要在 build.gradle 里开启 testLogging」；失败时的 `N tests completed, M failed` 与开了 testLogging 的逐条 `PASSED`/`FAILED` 行已能解析（2026-11-09 补）。

## 8. 选择与排序（`bestof` 扩展）

`Candidate` 新增字段：`tests: int`（判据读出的测试数）、`touched_tests: bool`（改动是否碰到探测到的测试文件）、`votes: int`（同模型 A/B 净胜票）。

`pick` 的排序键（全部来自可观测事实，没有一条来自模型自述）：

1. `verified`（判据通过 + 未过期）—— 硬门槛，沿用现状
2. 回归门通过
3. `votes`（同模型 A/B 位置对调后的净胜）
4. `tests`（多 = 覆盖更完整）
5. 改动面小（files / 行数）
6. `not touched_tests`
7. `cost`
8. `id`（稳定排序）

报告必须写明用了哪条规则选中，例如「3 个候选都通过判据，A/B 净胜 2:0 选中 cand-2」。

## 9. 安全边界

| 约束 | 理由 |
|---|---|
| 判据命令不能被模型改 | 不变量 8；否则「测试通过」=「不用测」 |
| 探测来的判据首次需用户确认 | 陌生仓库不能自动执行它的脚本 |
| 只读 / 计划模式：allout 完全禁用 | 权限是硬边界（AGENTS.md） |
| 项目级 `.ee/config.toml` 只能收紧 | 否则陌生仓库能自己开并行改代码 |
| 候选不派子代理（不用 `task`） | 取消、判定、用量都在一个循环里；不扩大权限面 |
| 落选候选默认保留，不自动删 | `bestof.plan_cleanup` 的现有纪律 |
| 补丁应用失败时不覆盖主目录 | 宁可不生效，不能破坏用户工作 |
| 分叉前检查预算 | 已到线不再开新候选 |

## 10. 诚实边界（写进界面文案）

| 做不到 | 依据 |
|---|---|
| 让弱模型超过强模型 | Stroebl 2024 |
| 达到 oracle@N（候选里最好的那个） | 只读验证者会被自信错误骗过；只有测试能救回一部分 |
| 修复一定越过候选池 | Terminal-Bench 空结果（40% < 60%） |
| 测试覆盖不到的错误 | 执行门控的固有上限 |
| 探不到判据时仍然可靠 | 降级并标注「未验证」 |
| 100% 防止模型改测试 | Hook 拦 + 判据来自项目；无绝对保证 |
| 已有会话中途把强度拉满 | 会断前缀缓存，只在新会话生效 |

界面定位句（建议直接使用）：

> 全力以赴：把你的模型在这台机器上能给的推理预算全部用上——先一次做好，不行就按失败原因修，还不行才分头试。多数任务不会多花一分钱。

## 11. 落地顺序（顺序不可调）

| 阶段 | 内容 | 为什么排这里 |
|---|---|---|
| **0** | 修 `parse_tests`（七种 runner 形态，含 maven） | 无它则 Go/.NET/Ruby/PHP/Java-Node 用户拿到「永远失败」 |
| **1** | `core/probe.py` 判据探测 + 测试文件清单 | 零并发风险，体验改善最大 |
| **2** | `core/allout.py` + 开关 + 项目层收紧 | 让功能对所有用户成立 |
| **3** | 前端接 `goal_check` / `goal_done` + 开关 + 进度 | 长跑必须可见 |
| **4** | `bestof` 新排序键 + 同模型 A/B 评定 | 选择是瓶颈，比多采样更值 |
| **5** | Thread 层分叉 + 批评修复 + 回归门 + 自动写回 | 收益最大、风险最大，最后做 |

0~2 做完即可用（单路 + 判据闭环 + 自动推导），且不给任何用户造成负面影响。

## 12. 验收标准

## 13. 参考（2026-11-09 用真实浏览器核实）

- Kwok et al. 2026. *LLM-as-a-Verifier*. arXiv:2607.05391；仓库 `llm-as-a-verifier/llm-as-a-verifier`。核实点：Terminal-Bench V2 86.5%（bo3：Pass@1 79.4%、oracle 92.1%）；SWE-Bench Verified 78.2%；弱验证者（DeepSeek V4.1 Flash 验证 Opus 5.5 轨迹）63.1→66.2 / 64.8→69.2；`criteria/terminalbench4.md` 写明「自述不算证据」。局限：需要 logprobs —— ee 不走这条路。
- Stroebl, Kapoor, Narayanan. *The Limits of Inference Scaling Through Resampling*. arXiv:2411.17501。核实点：假阳性设上限；最优 K 常 <10。
- Snell et al. 2024. arXiv:2408.03314。核实点：compute-optimal 比 best-of-N 效率高 4 倍。
- Kalayci, Raman, Dughmi. arXiv:2510.01394。核实点：同等质量少 15–35% 生成。
- AI21, 2026-07. *Improving Best-of-N with Budget-Aware Execution for SWE Agents*。核实点：约 50% 单 rollout 解决；级联最多省 44%；并行早停最多快 25%。
- `maverick-tr/agent-ultramode` PAPER.md。核实点：reasoned A/B 87.6% 平 88.0%±0.6（调用 576 vs 4320）；repair safe-union 91.7% > oracle 87.5%；Terminal-Bench 空结果；温度阶梯 0/.3/.6/.9/1.1；N 是预算不是配额。
- `aura-farming/pqa`。核实点：选择门控在可执行验证器上；无套件标 UNVERIFIED。
- `wolfiesch/omp-best-of`。核实点：脏树拒绝、父 HEAD 未变才 apply、单一存活候选跳过验证。
- `SWE-agent/SWE-agent` issue #1492。核实点：n>1 重试重复计费 → 候选级归因必要。
- 主流产品现状（2026-11）：Cursor 3 `/best-of-n` 跨模型并行 worktree、父 agent 给评论、用户自选，**无测试门控自动选优**，且社区反馈脆弱；Claude Code 有 subagents / agent teams / worktrees / dynamic workflows，无内置测试门控 best-of-N；Codex CLI 无。→ 本功能是差异化空间。
