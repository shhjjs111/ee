# 全力以赴（allout）：让每个模型都跑到它自己的极限

状态：**设计，未实现**
日期：2026-11-08
作者：ee
相关：`roadmap-current.md`、`2026-10-29-t10-b-goal-loop.md`、`2026-10-28-stabilization-and-d6.md`

## 0. 一句话

一个会话级开关。打开后，ee 把**这个用户、这个模型、这台机器**能给的全部推理预算，自动花在「把活真正做到通过验证」上——不是花在「多说几遍」上。

**核心定位（必须先说清，否则整份设计会被误读）：**

> 目标不是「弱模型超过强模型」，而是「**每个模型都逼近自己的上限**」。

前者不可能（Stroebl et al. 2024：*no amount of inference scaling of weaker models can enable them to match the single-sample accuracy of a sufficiently strong model*）。后者可以做到，而且有明确的工程抓手。

这决定了所有取值的推导方向：**上限来自模型与机器，不来自一个写死的数字**。

---

## 1. 为什么这个功能值得做

### 1.1 单次尝试的失败是「偶发」而非「能力不足」

| 证据 | 数字 |
|---|---|
| AI21（SWE-rebench，GPT-5.2） | **约 50% 的任务单次 rollout 就解决**，但固定策略对每个任务都跑 5 次 |
| llm-as-a-verifier（Terminal-Bench 2.1，deepseek-v4-flash） | Best-of-3：Pass@1 79.4% → 自验证 **86.5%**；Oracle **92.1%** |
| 同上，Best-of-5 | 78.7% → **88.0%**；Oracle **96.6%** |

两点结论：

1. **一半的任务不需要加班**。对它们，allout 必须几乎零额外成本——这是「预算不是配额」的由来。
2. **成功候选常常已经存在，只是没被选中**。Best-of-5 时 oracle@5(96.6%) 与实际(88.0%) 差 **8.6 个百分点**——这些分全丢在「选择」环节。这个环节比「多采样几次」更值得投入。

### 1.2 同一模型内的提升是真实的，且不是靠运气

同一篇论文的另一组实验（Terminal-Bench 4.0，**弱模型充当验证者**去评强模型的候选）：Best-of-3 63.1% → **66.2%**，Best-of-5 64.8% → **69.2%**。

即：**验证者的能力可以弱于生成者，仍然有效**。这直接说明 allout 不需要「更聪明的裁判模型」，只要判据是客观的。

### 1.3 修复能突破采样的天花板

[agent-ultramode](https://github.com/maverick-tr/agent-ultramode) 的实测：SWE-bench Lite 24 题 **91.7%**，而它自己候选池的 oracle@5 只有 **87.5%**。

多采样有硬天花板（oracle@N），**按失败原因修复能穿过它**。而 ee 的 `run_goal` 已经是这个机制——这是本功能最重要的现成资产。

## 2. 设计原则（每条都有依据，不是偏好）

### P1　预算不是配额

> "**N is a budget, not a quota.** The moment an attempt passes your tests, ultra takes it and abandons the rest." —— agent-ultramode

固定 N 路对「50% 一次就成」的任务是纯浪费。因此：

- 默认**一次尝试**
- 失败才加注
- 一旦通过，立即停止一切后续花费

### P2　先便宜后贵（cascading）

> "Cascading ... **up to 44% saved on compute**" —— AI21
> "our adaptive strategy can obtain the same performance as non-adaptive Best-of-N while requiring **15-35% fewer generations**" —— [Optimal Stopping vs Best-of-N](https://arxiv.org/html/2510.01394)

顺序必须是：单路 → 按失败输出修 → 才分叉。

### P3　判据来自项目，不来自模型

这是 ee 的硬不变量，不可协商：

- `ee/ee/core/goal.py:13` ——「判据由用户给，模型不能改（见任务书不变量 8）」
- `ee/ee/server/threads.py:80` ——「判据只从 start_turn 这条入口来，模型无法写入——那会让"测试通过"变成"不用测"」

若允许模型自己定判据，功能会立刻退化成「模型宣布自己成功」。因此判据只能来自：
1. 用户在「目标」菜单里显式填写的命令（已有能力）
2. **从项目文件里探测**——`pyproject.toml`、`package.json` 等是**项目作者**写下的事实，不是模型写的

### P4　没有验证器就必须诚实

> "**selection is gated on the verifier** ... A high-conviction branch that fails its tests is a recorded failure, not a shipped feature. CI enforces this; **there is no bypass**." —— [PQA](https://github.com/aura-farming/pqa)
> "**No suite? The result is flagged UNVERIFIED.**"

探测不到判据时，allout **降级而非假装**：做单路，明确标注「未验证」，不承诺质量。

### P5　并行只提升「至少一个通过」的概率

并行有 oracle@N 上限，且 3→5 的边际收益只有 1.5pp（verifier 论文）。所以：

- N 硬上界 **3**
- 并行只在「修复也失败」之后才启用
- 并行不能替代修复

### P6　写回必须是自动的，且不能要求主目录干净

用户明确要求：**打开开关就能用**。因此不能沿用 `worktree.merge`（`ee/ee/core/worktree.py:455` 要求主目录无未提交改动——而 ee 刚改完代码时主目录必然是脏的）。

已验证可行的路径（见 §7.3）：从 `agent_base..HEAD` 提取补丁 → `git apply` 到脏主目录。补丁天然不含主目录的脏改动，因此能干净应用且保留用户未提交的工作。

## 3. 火力如何推导（回应「每个用户都火力全开」）

### 3.1 原则：上限由「模型 × 机器 × 项目」共同决定

ee 的 `Profile` 已经带有决策所需的全部字段（`ee/ee/core/providers/profiles.py:36-74`）：

| 字段 | 已知取值 | 用途 |
|---|---|---|
| `context_window` | 131072（glm/qwen/doubao）～1000000（deepseek/gemini） | 能容纳多少并行候选的上下文 |
| `max_output` | 8192 ～ 64000 | 单次修复能输出多少改动 |
| `effort_param` / `effort_levels` | gpt/gemini/deepseek 支持；claude/kimi/glm/qwen 不支持 | 能否把推理强度拉满 |
| `parallel_tools` | 全部为 true | 一步内能否并派 |
| `price` | 各不同 | 成本估算 |

**没有任何一处可以写死数字。**

### 3.2 输出：一个可解释的 `AlloutPlan`

```python
# ee/ee/core/allout.py（新建）

@dataclass(frozen=True)
class AlloutPlan:
    """一次 allout 的火力配置。所有字段都必须能向用户解释。"""
    candidates: int          # 后段并行路数（1 = 不并行）
    max_rounds: int          # 判据判定的总轮数
    effort: str              # 本会话应使用的推理强度档
    max_steps: int           # 单个候选的步数预算
    reasons: list[str]       # 为什么是这个值（界面直接显示）
    degradations: list[str]  # 降级原因（空 = 无降级）
    verified: bool           # 是否有客观判据；False 时只能单路
```

### 3.3 推导规则（每条都要产出 `reasons`）

```python
def derive(*, config, profile, project, machine) -> AlloutPlan:
    reasons, degr = [], []

    # ---- 判据：没有它就不存在"跑到极限"，只能降级
    if project.goal is None:
        degr.append("没有探测到可执行的测试命令：只能单路尝试，结果标注「未验证」")
        return AlloutPlan(candidates=1, max_rounds=1, effort=_max_effort(profile),
                          max_steps=_steps(profile, config, 1), reasons=reasons,
                          degradations=degr, verified=False)

    # ---- 推理强度：能否拉满取决于模型是否支持 effort 参数
    effort = _max_effort(profile)          # 不支持则原样返回 ""，不发参数

    # ---- 并行路数：min(机器, 上下文, 闸门, 硬上界)
    n_cpu  = max(1, machine.cpu_count)
    by_cpu = clamp(n_cpu // 4, 1, 6)                  # 16核→4, 8核→2, 4核→1
    by_ctx = 3 if profile.context_window >= 128_000 else 1
    by_gate = max(1, int(config.subagent.max_parallel))   # 默认 3
    by_cap = 3                                          # P5 硬上界
    candidates = min(by_cpu, by_ctx, by_gate, by_cap)

    # ---- 轮数：修复优先于并行
    max_rounds = 2 if candidates == 1 else 3

    # ---- 步数：只放宽到模型本身的上限内
    max_steps = _steps(profile, config, candidates)

    reasons.append(f"并行 {candidates} 路：CPU {n_cpu} 核 / 上下文 {profile.context_window//1000}k / 上限 {by_cap}")
    reasons.append(f"推理强度：{effort or '该模型不支持调节，按默认档'}")
    return AlloutPlan(...)
```

**关键点：`reasons` 不是装饰。**界面必须显示「全力以赴 · 3 路 · 16 核 · 上下文 1M」，否则用户无法理解为什么不是更多路，也无法判断是否该换模型。

### 3.4 各模型的推导结果（预演，用于写测试）

| 模型档案 | ctx | effort 档 | CPU 16 核时的 candidates | 说明 |
|---|---|---|---|---|
| deepseek | 1M | max | 3 | 上下文充裕，但受硬上界 3 |
| gemini | 1M | max | 3 | 同上 |
| gpt | 272k | max | 3 | |
| claude | 200k | 默认 | 3 | 不支持 effort 参数，强度用默认 |
| kimi | 262k | 默认 | 3 | |
| glm / qwen / doubao | 131k | 默认 | 3 | 刚好过 128k 门槛 |
| 8 核机器 + deepseek | 1M | max | 2 | 受 `by_cpu` 限制 |
| 4 核机器 + 任意 | 任意 | 任意 | 1 | 只单路 + 修复 |

### 3.5 为什么 `by_cpu = cpu // 4`

不是拍脑袋。依据是**本项目自己的实测**：`AGENTS.md` 记录 `-n auto`（16 路）会红 2 条测试，而 `-n 8` 全绿。测试本身吃 CPU，并行候选各跑一遍测试时，超过 CPU 承载会产出**假失败**——那会让功能比不开还差。

## 4. 执行流程

```
开关打开
   ↓
【探测】core/probe.py 读项目文件（只读，不跑命令）
   ↓ 探不到 → 降级：单路 + 标注「未验证」（P4）
   ↓ 探测到
【轮 1】单路正常做 → 判据判定
   ↓ 通过（约 50%）→ 结束，零额外成本（P1）
   ↓ 失败
【轮 2】把「判据命令 + 失败输出」喂回去修（run_goal 现有能力）
   ↓ 通过 → 结束
   ↓ 失败
【轮 3】同一步内分叉 2~3 路（各自 worktree、互相 blind）
        第一个通过判据的 → 立即 cancel 其余（P1）
        ↓
【写回】git diff agent_base..HEAD → git apply 到主目录（P6）
        ↓
【报告】goal_check / goal_done 推给界面；写明用了哪条规则选胜者
```

### 4.1 为什么并行必须在「同一步」内

`ee/ee/core/session.py:1663` —— 同一步内 `asyncio.gather(*tasks)`。子代理是 `task` 工具调用的生命周期（`ee/ee/tools/agent.py:44` `await run_subagent(...)`）。

**跨步无法中途取消已派出的候选**：它们各自跑完，钱已经花掉。因此「一次成功立即 cancel 其余」只能是**同一步内的多个 `task` 调用**。

### 4.2 取消时会发生什么（已核实）

- `ee/ee/core/subagent.py:495` —— `except asyncio.CancelledError: await _close(gen); _merge_usage(...); up(SubagentEnd(..., "interrupted", ...)); raise`
- **不会调 `finish_agent`，也不会删 worktree**
- 因此取消的候选会留在 worktree 列表里 → 需要 `plan_cleanup`（`ee/ee/core/bestof.py:131`）配合清理，否则列表堆积

## 5. 判据探测（`core/probe.py`）

### 5.1 探测什么

只读文件，**不跑命令**（跑命令会让「打开开关」这个动作产生副作用，不可接受）。

| 文件 | 取值 | 命令 |
|---|---|---|
| `pyproject.toml` | `[tool.pytest.ini_options]` 或 `[tool.uv]` 存在 | `python -m pytest -q` |
| `package.json` | `scripts.test`（排除 `no test specified`） | `npm test` |
| `Cargo.toml` | 存在 | `cargo test` |
| `go.mod` | 存在 | `go test ./...` |
| `pom.xml` | 存在 | `mvn -q test` |
| `build.gradle`/`.kts` | 存在 | `./gradlew test` |
| `*.csproj`/`*.sln` | 存在 | `dotnet test` |
| `Gemfile` + `spec/` 或 `test/` | 存在 | `bundle exec rspec` |
| `composer.json` | `require-dev` 含 phpunit | `vendor/bin/phpunit` |

多个命中时按「项目根 → 子目录」优先；同时命中多种时取**最外层唯一**的那个，若并列则降级并要求用户手填（不猜）。

### 5.2 探测不到怎么办

**降级，不猜。** 界面提示：「没找到测试命令，本次只能做单路尝试，结果不保证正确性。可以在『目标』里填一条命令启用完整模式。」

## 6. 必须修的现有缺陷

### 6.1 `parse_tests` 对多数语言返回 0（**功能前提**）

实测（本机 `.venv`）：

```
pytest   15 ✅    vitest  12 ✅    jest  12 ✅    cargo 12 ✅    deno  12 ✅
go test   0 ❌    dotnet   0 ❌    mocha  0 ❌    rspec  0 ❌    phpunit 0 ❌
```

`ee/ee/core/goal.py:122` 只认 `N passed` / `N failed` / `collected N items` / `N tests passed`。

`Verdict.met`（`goal.py:55-62`）要求 `tests >= min_tests`，读不到按 0：

> `zero_tests：命令成功但没收集到任何测试（需要 ≥1 个）。退出 0 不等于验证通过`

**后果**：Go / .NET / Mocha / RSpec / PHPUnit 项目里，`go test ./...` 全绿也判不通过 → allout 变成「无限重试、永远失败、烧光预算」。**必须第一个修。**

要加的形态：

```python
_GO_OK   = re.compile(r"^ok\s+\S+", re.M)                                   # go test
_GO_FAIL = re.compile(r"^(?:---\s+)?FAIL\b", re.M)
_DOTNET  = re.compile(r"Failed:\s*(\d+),\s*Passed:\s*(\d+)", re.I)
_MOCHA   = re.compile(r"(\d+)\s+passing", re.I)                             # 亦有 "N failing"
_RSPEC   = re.compile(r"(\d+)\s+examples?,\s*(\d+)\s+failures?", re.I)
_PHPUNIT = re.compile(r"OK\s*\((\d+)\s+tests?", re.I)
_BUN     = re.compile(r"(\d+)\s+pass\b", re.I)
```

`go test` 特殊：成功只打 `ok  pkg  0.12s`，**没有**「N tests passed」。须数 `ok` 行数当 tests；出现 `FAIL` 行时即便有 `ok` 也算失败。

### 7.3 自动写回（已实测验证）

```python
def apply_winner(cand_info: dict, main_cwd: Path) -> dict:
    """把候选的改动以补丁形式应用到主目录。不要求主目录干净。"""
    base = cand_info["agent_base"]          # 已含主目录脏改动的基线提交
    # 1. 提取候选自己的改动（天然不含主目录脏改动）
    code, patch, err = run_capture([git, "diff", "--binary", base, "HEAD"], cwd=cand_info["path"])
    # 2. 应用到主目录（脏也能应用）
    code, _, err = run_capture([git, "apply", "--binary", "--whitespace=nowarn", pfile], cwd=main_cwd)
    # 3. 失败 → 不覆盖，报告并保留 worktree
```

实测记录（2026-11-08，临时目录，已清理）：

```
主目录脏：a.txt 含 MODIFIED-BY-EE
候选 worktree 基线含该改动（_sync_dirty，worktree.py:491）
候选加 NEW-SOLUTION 并提交
git diff agent_base..HEAD →  补丁只含 "+NEW-SOLUTION"
git apply 到脏主目录 → APPLY-OK
结果：主目录 = MODIFIED-BY-EE + NEW-SOLUTION，脏状态保留
```

**不用 `worktree.merge`**：它要求主目录干净（`worktree.py:455`），全自动场景下必然失败。

## 8. `bestof.pick` 的质量信号（选择是真正的瓶颈）

现状 `ee/ee/core/bestof.py:127`：

```python
verified.sort(key=lambda c: (float(c.cost or 0.0), c.id))
```

同等通过时按成本选，`id` 是自动生成的随机名 → **等于随机**。自动写回时这不可接受。

自动模式下的排序键（**每一条都要能向用户解释**）：

```
1. 判据通过的测试数（多 = 覆盖更完整）        # 来自 Verdict.tests，客观
2. 改动面更小（files/行数少 = 风险低）        # 最小 diff 通常更对
3. 未触碰判据/测试文件（触碰 = 可疑）          # 客观
4. 成本更低（同等条件下）                     # 现有行为
5. id（稳定排序，不碰运气）
```

原则：**这四条全部来自可观测的事实，没有一条来自模型的自我评价**（`Candidate.self_reported_ok` 明确「不参与判定，只记录」，`bestof.py:37`）。

报告里必须写明用了哪条规则选出来，例如：
> 「3 个候选都通过判据，按『测试覆盖更完整』选中 cand-2（142 个测试 vs 96 / 88）」

## 9. 全自动下的安全边界

用户要「一个开关就火力全开」，但以下红线不放开：

| 约束 | 理由 |
|---|---|
| 判据命令不能被模型改 | 不变量 8；否则「测试通过」=「不用测」 |
| 只读/计划模式：allout 完全禁用 | 权限是硬边界（`AGENTS.md`） |
| 项目级 `.ee/config.toml` 只能收紧，不能打开 allout | `config.py:218`；否则陌生仓库能自己开并行改代码 |
| 落选候选默认保留，不自动删 | `bestof.py:131` 的现有纪律；误删不可逆 |
| 补丁应用失败时不覆盖主目录 | 宁可不生效，不能破坏用户工作 |
| 预算：并行到线只问一次 | `core/budget.py` 现有行为 |

## 10. 诚实的边界：这个功能做不到什么

必须写进用户可见的说明，不能靠默认理解：

| 做不到 | 依据 |
|---|---|
| 让弱模型的绝对水平超过强模型 | Stroebl 2024 |
| 达到 oracle@N（候选里最好的那个） | verifier 论文实测丢 8.6pp；缺质量信号 |
| 保证一定比不开更快 | 50% 任务零成本，但剩余任务可能多花 |
| 探不到判据时仍然可靠 | P4：降级并标注「未验证」 |
| 100% 防止模型改测试 | 只能 Hook 拦 + 判据来自项目；无绝对保证 |
| 跨步取消已派出的候选 | ee 架构限制（`session.py:1663` 只同步内 cancel） |

**对外的定位句（建议直接用作界面文案）：**

> 全力以赴：把你的模型在这一台机器上能给的推理预算全部用上——先一次做好，不行就修，还不行才分头试。多数任务不会多花一分钱。

## 11. 落地顺序（顺序不可调）

| 阶段 | 内容 | 为什么排这里 |
|---|---|---|
| **0** | 修 `parse_tests`（5 种语言） | 无它则 Go/.NET/Ruby/PHP 用户拿到的是「永远失败」 |
| **1** | `core/probe.py` 判据探测 | 零并发风险，体验改善最大 |
| **2** | 开关 + `derive()` + 项目层收紧 | 让功能对所有用户成立 |
| **3** | 前端接 `goal_check`/`goal_done` | 长跑必须可见 |
| **4** | `bestof.pick` 质量信号 | 选择是瓶颈，比多采样更值 |
| **5** | 子代理接 `run_goal` + `task` 扩参 | 阶段 3 并行（收益最小、风险最大） |

0~2 做完就能用（单路 + 判据闭环 + 自动推导），且不给任何用户造成负面影响。
