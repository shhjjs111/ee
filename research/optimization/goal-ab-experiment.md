# Goal 失败反馈 A/B 对照实验报告

日期：2026-10-30
模型：deepseek-flash（DeepSeek V4.1-Flash）
实验执行：天枢（本会话）

## 结论（一句话）

在需要从测试输出定位的 bug 上，把「判据命令 + 失败输出」送进模型输入，让模型
平均少 1 次请求、成本低约 13.5%。方向稳定，但样本 n=5 不足以宣称统计显著。

## 被测改动

- **实验组（current）**：`87883a0` 起的 Goal 反馈——续跑时把判据命令、退出码、
  测试计数、失败输出拼成有边界的数据块送给模型。
- **对照组（baseline）**：`607ec92`——Goal 续跑只发固定文案「继续，直到判据通过」。

两组代码差异仅此一处；工具、模型、权限、超时参数完全一致。

## 方法（吸取第一次污染教训）

1. 每组用独立 git 仓库，初始 bug 用 commit 锁定（不依赖工作区残留）。
2. 每次 run 前 `git reset --hard <initial>` 回到完全相同的起点。
3. 判据固定为 `python -m pytest -q test_parse.py`，模型只能改被测文件。
4. 每组各 5 次，交错分批执行（先各 3 次，再各 2 次），降低时段波动影响。

第一次实验（简单 bug `1+1==3`）因状态污染作废：对照组初始文件已被上一组
实验修好，导致它第一轮判据直接通过、模型根本没跑。本次用 git reset 严格隔离，
不复现该问题。

## 任务设计

```python
# impl.py（注入的 bug：空值被替换成 "<empty>"，源码看起来"合理"）
def parse_spec(s):
    out = {}
    for item in s.split(";"):
        if not item.strip():
            continue
        k, v = item.split(":", 1)
        out[k] = v if v else "<empty>"   # bug：空值应保留为空字符串
    return out
```

测试 `test_empty_value` 断言 `parse_spec("a:;b:x") == {"a": "", "b": "x"}`。
这个 bug 的关键在于：读源码时 `<empty>` 看起来像合理的防御，只有测试输出
才能指出"预期是保留空字符串"。这正是失败反馈应该发挥作用的任务类型。

## 解读

1. **轮次相同、请求数不同**是关键。两组的 Goal 都是「先判后跑」（第一轮判据
   先跑一次），所以 rounds 都是 2。差异在修复回合**内部**：
   - 有反馈：模型第一轮就拿到"空值必须保留为空"的测试输出，一次改对。
   - 无反馈：模型只拿到"继续，直到判据通过"，得重新读源码、试错，
     多花 1 次请求才定位到 bug。

2. **绝对幅度小**：每次省约 1 次请求、0.001 元。在 flash 这种便宜模型上单次
   收益很小，但方向明确。

3. **外推**：收益在更难的任务上会放大——失败原因藏在复杂输出里时，无反馈的
   模型可能多试很多次甚至卡在 max_steps。本实验的 1 次请求差距是下限。

4. **局限**：n=5 是方向性证据，不是统计显著结论；单一任务、单一模型（flash）。
   换更强模型（pro）或更简单任务，差异可能消失。

## 已证伪/存疑

- 简单任务（`1+1==3`）上，两组的差异在噪声范围内（current 0.00640 vs
  baseline 0.00686）。失败反馈对"读一眼就能改"的任务无收益——这符合预期，
  因为那种任务根本不依赖失败输出。

## 成本

两次任务共 20 次付费运行（10 简单 + 10 复杂），总计约 0.16 元。
